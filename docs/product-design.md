# Design: Wishlist in Calendar — Weekend Magic Feed

## Problem Statement

Wishlist in Calendar turns a user's Steam wishlist into a system-level calendar subscription.

The user pastes a Steam Profile URL or SteamID, imports a public wishlist, previews upcoming relevant moments, then subscribes to a dynamic `.ics` feed in Apple Calendar, Google Calendar, Outlook, Fantastical, or any calendar app that supports `webcal://`.

The product is not a Steam database, discount site, or game news site. It is a quiet calendar layer for games the user already cares about.

## What Makes This Cool

The magic is not "Steam data in another UI." Steam already has a Personal Calendar inside Steam Labs. That validates the calendar metaphor, but it solves discovery inside Steam.

Wishlist in Calendar solves integration into the user's life calendar.

Steam's version is:

- a Steam webpage
- discovery-heavy
- recommendation-driven
- inside the Steam attention loop

Wishlist in Calendar is:

- `.ics` / `webcal://`
- system-level calendar subscription
- Apple / Google / Outlook / Fantastical compatible
- quiet, ambient, and personal
- focused on games the user already wants

The user should feel: "My Steam future now lives beside my actual future."

## Constraints

- First version is a personal project, not a VC-scale startup plan.
- The product should still be shareable and donation-friendly.
- Core audience starts with Steam users who track wishlisted game releases and sale periods.
- Steam official wishlist APIs are limited or unstable; public wishlist import must fail gracefully.
- Steam festivals are useful, but secondary. They are a background layer, not the main product.
- Donation CTA should appear after successful value delivery, not before the user subscribes.
- zh / en, responsive layout, dark mode, and Steam + Apple visual tension are part of the product feel.

## Premises

1. Users do not primarily need Steam event information itself. They need to know when games on their own wishlist deserve attention.
2. Calendar is stronger than notifications here because calendar carries future plans and anticipation, not interruptions.
3. First version must still be valuable when wishlist import fails: Steam event subscription, manual add, or clear public wishlist guidance.
4. Feed must continuously update prices and release states. Otherwise it is a one-time export, not ambient software.
5. Sharing and donations should center on "my Steam future timeline," not a generic tool feature list.
6. Steam Personal Calendar validates the timeline metaphor, but leaves space for system-level calendar integration.

## Cross-Model Perspective

Codex's cold read pushed the design in one important direction: do not position this as "Steam wishlist on a calendar" because Steam already has an internal Personal Calendar. Position it as a cross-calendar, ambient integration layer.

Codex's strongest version was a living "My Steam Future Timeline" where each game can become a living calendar object:

- wishlist added
- demo available
- Steam Next Fest appearance
- launch week
- first discount
- historical-low discount
- reviews crossed threshold
- play this weekend

For v1, we keep that as the long-term direction, but avoid social graph, historical-low tracking, and review thresholds until the core feed works.

Codex's weekend recommendation:

1. Input Steam profile URL or SteamID.
2. Resolve wishlist if public.
3. Generate preview list with name, release status/date, price/discount when available.
4. Generate one dynamic `.ics` URL.
5. Include release events and major Steam festival/sale events; keep discount details inside sale-period descriptions for later V1 Launch.
6. Add manual appID/game add fallback.
7. Add shareable `/u/slug` page showing "My Steam Future Timeline."
8. Add donation button after successful calendar subscription.

## Approaches Considered

### Approach A: Weekend Magic Feed

Public wishlist import + dynamic `.ics` feed + preview. Weekend Prototype event types are limited to:

- exact wishlist release dates
- major Steam sales and festivals

V1 Launch can add sale-period descriptions that summarize discounted wishlisted games.

Effort: M  
Risk: Medium

Pros:

- Proves the full magic loop in one weekend-scale build.
- Gives users a real calendar subscription, not just a mockup or export.
- Keeps Steam festivals as useful background without letting them dominate the product.
- Supports sharing and donation after value is delivered.

Cons:

- Does not yet include historical low prices, review thresholds, demo detection, or social signals.
- Public wishlist import may fail for private profiles or unstable Steam endpoints.
- Dynamic feed updates require a minimal persistence and refresh strategy.

### Approach B: Living Attention Timeline

Each wishlist game becomes a living object with state transitions over time: demo available, launch week, first discount, historical low, review milestone, Next Fest appearance, and "play this weekend" prompts.

Effort: XL  
Risk: High

Pros:

- Best long-term expression of the product philosophy.
- Creates a stronger reason to keep the calendar subscribed over months.
- Makes the product feel alive rather than exported.

Cons:

- Requires scheduled crawling, persistent snapshots, state diffing, price history, and more data quality work.
- Easy to overbuild before proving that users want Steam wishlist moments in their calendar.
- More failure modes and more user trust risk.

### Approach C: Share-first Timeline

Build `/u/slug` as the primary artifact: "My Steam Future Timeline," optimized for screenshots, sharing, OG images, bilingual copy, and donation conversion. Calendar subscription becomes the save action.

Effort: M  
Risk: Medium

Pros:

- Strongest viral and donation path.
- Makes the product feel like identity and anticipation, not a utility.
- Easier for users to understand before installing a calendar subscription.

Cons:

- Risks under-serving the core promise if `.ics` behavior is not strong.
- Could drift into a pretty sharing page instead of an ambient calendar layer.

## Recommended Approach

Choose Approach A: Weekend Magic Feed, but narrow it harder.

The prototype should prove one question:

> Will a user put Steam wishlist time nodes into the calendar they actually live in?

The first version should not try to prove sharing, donation, social identity, or a beautiful timeline page. Those can wait until calendar subscription itself feels valuable.

Scope is split into two cuts:

### Weekend Prototype

1. Input Steam Profile URL or SteamID.
2. Read a public wishlist.
3. Extract games with exact release dates.
4. Add a small fixed list of Steam major events.
5. Generate a preview.
6. Output a valid `.ics` feed.
7. Subscribe successfully in Apple Calendar.

Do not build:

- accounts
- Steam login
- donation
- `/u/{slug}`
- social images
- historical lows
- review thresholds
- genre fests
- full search
- complex customization
- separate per-game discount events

### V1 Launch

1. Import or fallback.
2. Preview value.
3. Persist feed settings behind a private token.
4. Subscribe with Apple / Google / Outlook guidance.
5. Add sale-period descriptions that summarize discounted wishlist games.
6. Offer a minimal unlisted share page only after feed subscription is proven valuable.

Do not let share, donation, or visual polish change the prototype scope.

## Product Flow

### 1. Landing

Hero copy:

> Put your Steam wishlist into your calendar.

Supporting copy:

> Steam has a calendar inside Steam. This puts your wishlist into the calendar you actually live in.

Input:

- Steam Profile URL
- SteamID
- manual Steam store URL or appID fallback

Full game search is deferred until after v1.

Manual fallback behavior: when the user enters a Steam store URL or appID, fetch metadata for that app, add it to the selected appIDs list, show it in preview, and persist it into the same feed settings.

Primary CTA:

- Preview my Steam timeline

Secondary CTA:

- Subscribe only to Steam events

### 2. Import

The app resolves Steam identity and attempts public wishlist import.

Possible states:

- success: wishlist games loaded
- private wishlist: explain how to make wishlist public or use manual add
- invalid profile: ask for SteamID/profile URL again
- Steam unavailable: offer Steam event calendar and manual add

### 3. Preview

Calendar preview groups future moments:

- `🎮 Hollow Knight: Silksong releases`
- `🛒 Steam Summer Sale begins` with discounted wishlist games in the description
- `🛒 Steam Summer Sale begins`
- `🧪 Steam Next Fest begins`

Weekend Prototype controls:

- Include wishlist releases with exact dates
- Include major Steam events
- Emoji titles on
- Steam links in descriptions

V1 Launch controls:

- Include sale-period summaries in Steam major event descriptions
- Include TBD games on share page only, never as dated calendar events
- Locale fixed at feed creation

Deferred controls:

- Per-game discount events
- Genre fests
- Reminders
- Unreleased-only filtering
- Historical-low filtering
- Full title style customization

### 4. Subscribe

Generate:

- private random feed token, not derived from SteamID
- `.ics` HTTPS URL
- `webcal://` URL for clients that support it
- copyable HTTPS feed URL for Google Calendar

Buttons:

- Add to Apple Calendar via `webcal://`
- Add to Outlook via documented subscribe link or copied URL
- Google Calendar instructions with copyable HTTPS feed URL
- Copy feed URL

V1 should not promise perfect one-click Google Calendar subscription. The Google path is: copy feed URL, open Google Calendar, add calendar by URL.

### 5. Share

Share page is not part of the Weekend Prototype.

For V1 Launch, create an unlisted public page only after the user chooses to share:

`/u/{random-slug}`

The share slug is separate from the private calendar feed token. The share page never exposes the `.ics` URL.

Title:

> My Steam Future Timeline

Content:

- next Steam major event
- next wishlisted release
- sale-period summary if available
- optional Steam event overlay

Privacy defaults:

- no Steam profile link unless user opts in
- no feed URL on the share page
- no account required
- random unguessable slug for v1

Sharing matters because the product spreads through identity: "these are the games I'm waiting for."

### 6. Donate

Donation is not part of the Weekend Prototype.

For V1 Launch, show donation CTA only after successful calendar subscription.

Copy:

> If this saved your future self a few Steam checks, you can buy me a coffee.

## Event Model

### Weekend Prototype Event Types

1. Wishlist release event
   - date: exact known release date only
   - title: `🎮 {game} releases`
   - description: Steam link, price if available, source timestamp

2. Steam major event
   - date range: start/end dates
   - title: `🛒 Steam Summer Sale`
   - description: Steam event link if known

### V1 Launch Event Types

3. Steam sale period with wishlist discount summary
   - date range: sale start/end dates
   - title: `🛒 Steam Summer Sale`
   - description includes discounted wishlisted games, current price, discount percent, Steam links, and feed refresh timestamp

Do not create separate per-game discount events by default. Discounts are status details inside a sale period, not primary calendar events.

Power user mode, deferred:

- Track each wishlist discount as a separate sale-period calendar event
- Default off

Release states:

- exact date: calendar event
- month/quarter/year only: preview label, no calendar event in v1
- `Coming soon` / TBD: share page only, no dated calendar event

### ICS Requirements

- Use stable `UID` per feed event: `{feedToken}:{eventType}:{appID-or-eventID}`.
- Use all-day events for releases and Steam sales unless a source provides a meaningful time.
- Use `DTSTART;VALUE=DATE` for single-day release events.
- Use `DTSTART;VALUE=DATE` and exclusive `DTEND;VALUE=DATE` for sale ranges.
- Include `DTSTAMP` and `LAST-MODIFIED` from server generation time or source update time.
- Keep event UIDs stable when title, price, or description changes.
- If an event disappears, omit it from the next feed response; calendar clients will eventually remove it according to their refresh behavior.
- Target parser compatibility: Apple Calendar, Google Calendar by URL, Outlook by subscribed calendar URL.
- Copy should say feeds update automatically as the calendar app refreshes, not instantly.

### Deferred Event Types

- historical low discount
- demo available
- launch week window
- review threshold crossed
- friend also wants this
- play this weekend
- bundle availability

## Data Strategy

### Wishlist Import

Use public wishlist access only in v1.

Potential sources to verify during implementation:

- public wishlist page parsing
- Steam storefront wishlist endpoint, if still available
- wrapper library such as `python-steam-api`, only after verifying current endpoint behavior

### Game Metadata

Fetch or derive:

- appID
- name
- release date text
- release date confidence
- current price
- discount percent
- store URL

### Steam Events

Start with a manually maintained seed list for major events.

Do not build a full Steam event database in v1.

### Feed Refresh

Weekend Prototype can generate `.ics` on demand without persistence if needed.

V1 Launch feed must be dynamic, but calendar refresh timing is controlled by the user's calendar app. Copy must say: "updates automatically as your calendar app refreshes," not "instant updates."

V1 refresh policy:

- on-demand refresh when the `.ics` URL is requested
- 6-hour cache per feed and appID to avoid hammering Steam
- serve stale data if Steam fails
- background refresh is deferred unless the deployment platform has reliable cron support
- discount information appears inside sale-period descriptions, not as default standalone events

Minimum persistence for V1 Launch:

- private random feed token
- optional separate share slug
- source SteamID/profile
- selected appIDs
- enabled toggles
- locale fixed at feed creation
- created timestamp
- last successful refresh timestamp
- last attempted refresh timestamp

## Failure Paths

### Private Wishlist

Message:

> Your Steam wishlist looks private. You can make it public, paste specific Steam game links, or subscribe only to Steam events.

Actions:

- show public wishlist instructions
- manual add game
- subscribe only to Steam events

### No Upcoming Games

Message:

> Your wishlist has no dated upcoming releases right now. We can still track discounts and Steam events.

Actions:

- include sale-period discount summaries in V1 Launch
- include TBD section on share page
- include Steam events

### Steam Fetch Fails

Message:

> Steam did not respond. Your calendar feed will keep trying quietly.

Actions:

- create feed anyway if settings are valid
- mark preview as stale/unavailable
- retry later

## Visual Direction

Style:

- Apple-like spacing and clarity
- Steam dark accents, not full gamer clutter
- calendar-first layout
- quiet, not notification-heavy
- dark mode required
- zh / en copy from day one

Core visual motif:

A clean monthly or agenda-style timeline where Steam moments appear like holidays, moon phases, weather, or seasonal markers.

The UI should make game events feel calm and inevitable, not like ads.

## Success Criteria

Weekend Prototype is successful if:

1. A user can paste a public Steam profile and see exact-dated wishlist release events.
2. A user can preview a small set of Steam major events alongside wishlist releases.
3. The app outputs a valid `.ics` feed.
4. The feed can be subscribed to successfully in Apple Calendar.
5. The homepage clearly distinguishes this from Steam's internal Personal Calendar.

V1 Launch is successful if:

1. Private wishlist users still have a useful path: manual appID/store URL add or Steam event subscription.
2. Sale-period descriptions can summarize discounted wishlisted games without polluting the calendar with many discount alerts.
3. The feed can be subscribed to in Apple Calendar and added to Google Calendar by URL.
4. The share page makes sense without explanation, but only after calendar subscription value is proven.
5. Donation CTA appears only after the user has received value.

## Distribution Plan

This is a web service with hosted dynamic calendar feeds.

Distribution channels:

- public website at the product domain
- shareable `/u/{slug}` timeline pages
- `webcal://` subscription links
- copyable `.ics` feed URLs
- posts to Steam communities, Reddit, X, indie game communities, and personal networks once the first version works

CI/CD:

- deploy web app and feed server on merge to main
- run feed generation tests before deploy
- run one smoke test that validates a generated `.ics` file parses correctly
- later add scheduled feed refresh monitoring

## Dependencies

- Reliable enough Steam public wishlist ingestion.
- Steam app metadata and current discount retrieval.
- iCalendar generation library.
- Stable feed persistence.
- Clear locale strategy for zh/en.
- Deployment platform that supports dynamic routes plus on-demand caching; cron/background refresh is optional after v1.

## The Assignment

Before writing production code, ask 5 Steam users with public wishlists this forced-choice question:

> If your real calendar could keep only one kind of Steam information, which would you choose?
>
> A. Wishlist game release dates
> B. Wishlist game discounts
> C. Steam major sales / Next Fest
> D. I do not want Steam in my calendar

Then show them a tiny preview and ask:

> Which of these events would you keep, which would you delete, and would you subscribe in Apple Calendar?

Do not ask, "Would you use this?"

The answer determines whether V1 is truly a future anticipation layer or whether users mostly want a deal tracker.
