## Goal

Build the smallest prototype that validates:

> A user can put Steam wishlist release dates and major Steam events into Apple Calendar through a real `.ics` subscription.

This is not a deal tracker. Discounts are not default standalone calendar events. The prototype tests `Steam wishlist → real life calendar`.

## Step 0: Scope Challenge

### Scope accepted with reductions

The reviewed scope was reduced and clarified:

- Use **Next.js + Vercel**, not Cloudflare Pages, to avoid runtime adapter complexity.
- Do **Steam ingestion spike first**, before UI.
- Use **SteamID64 only** for the prototype. No vanity URL resolution, no Steam Web API key requirement.
- Use **SteamID URL feed** for prototype, not encoded appIDs and not KV token persistence.
- Use a third-party iCalendar library, but wrap it and lock output with golden tests.
- Keep route handlers thin; logic lives in four small modules.
- Add timeout + short cache for Steam requests.
- Configure Vitest + Playwright from day one.

### NOT in scope

- Accounts — no user model or auth needed to validate calendar subscription.
- Steam login — prototype only reads public wishlist via SteamID64.
- Vanity profile URLs — deferred; users must provide SteamID64.
- Donation — only after subscription value is proven.
- `/u/{slug}` share page — V1 Launch only, not Weekend Prototype.
- Social images — distribution feature, not validation requirement.
- Historical lows — would turn this toward deal tracking and require price history.
- Review thresholds — needs extra data source and not relevant to calendar subscription validation.
- Genre fests — manually burdensome and not core to prototype.
- Full search — manual fallback is appID/store URL later; not needed for first ingestion spike.
- Complex customization — default settings only.
- Separate per-game discount events — deferred power-user mode; default is sale-period description details.
- Google one-click subscription — V1 guidance only; Weekend Prototype validates Apple Calendar.
- Persistent private feed tokens — deferred until V1 unless SteamID URL proves too limiting.

## Architecture

### Chosen architecture

```
User browser
  │
  ├── GET /                         Landing + SteamID64 input
  │
  ├── POST/GET preview route         Validate SteamID64, fetch wishlist, map events
  │       │
  │       ▼
  │   steam-client
  │       ├── validate SteamID64 only
  │       ├── build public wishlist URL
  │       ├── fetch public wishlist
  │       ├── fetch app metadata when needed
  │       └── normalize errors
  │
  │   event-mapper
  │       ├── exact release date → release event
  │       ├── TBD/month-only → preview-only/excluded
  │       └── fixed Steam major events → date range events
  │
  └── GET /feed/{steamId64}.ics      Re-fetch wishlist with cache, map events, emit .ics
          │
          ▼
      ics-generator
          ├── iCalendar library wrapper
          ├── stable UID scheme
          ├── all-day DTSTART/DTEND
          ├── text escaping
          └── text/calendar response
```

### Module boundaries

1. `steam-client`
   - Input: SteamID64 only.
   - Builds `https://store.steampowered.com/wishlist/profiles/{steamId64}/`.
   - Fetches wishlist and metadata.
   - Applies timeout and short cache.
   - Returns typed success/error states.

2. `event-mapper`
   - Converts Steam app metadata + fixed Steam events into internal calendar events.
   - Only exact release dates become calendar events.
   - TBD, year-only, quarter-only, and month-only dates are excluded from feed.

3. `ics-generator`
   - Wraps chosen iCalendar library.
   - Owns UID, all-day event, date range, title/description, and response text behavior.
   - Has golden tests so the third-party library cannot silently change output shape.

4. Route handlers/pages
   - Landing page and preview UI.
   - Preview route orchestrates Steam client + event mapper.
   - Feed route orchestrates Steam client + event mapper + ICS generator.
   - Route handlers should not parse Steam HTML or hand-build `.ics` text.

### Runtime and deployment

- Stack: Next.js + Vercel.
- Deployment target: public Vercel HTTPS URL.
- Apple Calendar validation must happen against the deployed URL, not localhost.
- Feed route must set:
  - `Content-Type: text/calendar; charset=utf-8`
  - appropriate cache headers for prototype
  - no accidental static caching for dynamic feed route

## Data and feed identity

### Prototype feed URL

Use SteamID64 in the feed URL:

`/feed/{steamId64}.ics`

Rationale:

- User explicitly chose SteamID URL to preserve automatic wishlist changes.
- The feed re-fetches the public wishlist when calendar clients refresh.
- No appID snapshot, because wishlist additions should naturally enter the calendar.

Risks:

- URL exposes SteamID64.
- No per-user settings persistence.
- Repeated calendar refreshes can hit Steam.

Mitigations:

- SteamID64 is already public enough for public wishlist access.
- Add request timeout and short cache.
- Add input validation and item caps.
- V1 Launch can migrate to private random token + stored SteamID/settings if prototype proves value.

## Steam ingestion rules

### Accepted input

- SteamID64 string only for Weekend Prototype.
- Optional URL parsing may accept only the exact profile form and extract SteamID64:
  - `https://store.steampowered.com/wishlist/profiles/{steamId64}/`
  - `https://steamcommunity.com/profiles/{steamId64}`

### Rejected input

- Vanity URLs.
- Arbitrary URLs.
- Non-Steam hostnames.
- IDs that are not valid SteamID64 shape.

### Abuse and limits

- Validate input before any fetch.
- Hard-cap wishlist items processed in prototype. Recommended cap: first 100 apps until data behavior is understood.
- Add fetch timeout. Recommended default: 10 seconds per external request.
- Add concurrency limit for app metadata fanout. Recommended default: 5 concurrent requests.
- Serve partial preview with clear warning if some metadata fails.

## Event semantics

### Calendar events in Weekend Prototype

1. Wishlist release event
   - Only exact date.
   - All-day event.
   - Title: `🎮 {game} releases`.
   - Description: Steam store link and source timestamp.

2. Steam major event
   - Fixed manually seeded date range.
   - All-day range event.
   - Title: `🛒 Steam Summer Sale` or `🧪 Steam Next Fest`.
   - Description: event source or manually maintained note.

### Excluded from prototype calendar feed

- TBD
- Coming soon
- Year-only dates
- Quarter-only dates
- Month-only dates
- Per-game discount alerts

### Future discount model

Default V1 model is not per-game discount alerts. Steam major sale events can include discounted wishlist games in the description.

## ICS requirements

- Use stable UIDs:
  - Release: `steam-app-{appid}-release@wishlist-in-calendar`
  - Steam event: `steam-event-{eventId}-{year}@wishlist-in-calendar`
- Use all-day date values.
- Use exclusive `DTEND` for date ranges.
- Include `DTSTAMP` and `LAST-MODIFIED`.
- Keep UIDs stable if title/date/description changes.
- Response must be parseable by Apple Calendar.
- Golden tests must cover output shape and date range behavior.

## Failure modes

| Codepath | Failure | Test? | Handling | User sees |
|---|---|---:|---|---|
| SteamID validation | malformed input | Yes | reject before fetch | clear input error |
| Steam fetch | timeout | Yes | timeout + normalized error | retry/fallback message |
| Wishlist fetch | private/hidden wishlist | Yes | normalized private/empty state | public wishlist instructions |
| Wishlist fetch | HTML/403/bot block | Yes | normalized unavailable state | Steam unavailable message |
| App metadata | partial failures | Yes | partial results + warning | some games skipped warning |
| Date parsing | TBD/month-only | Yes | excluded from feed | preview note or omission |
| Event mapping | empty release list | Yes | show major events only | no dated releases message |
| ICS generation | bad escaping | Yes | golden test fails | not shipped |
| ICS generation | wrong DTEND | Yes | golden test fails | not shipped |
| Feed route | missing/invalid SteamID | Yes | 400 response | clear error text |
| Feed route | Steam unavailable | Yes | generate major events if possible or 503 | visible feed error/log |
| Apple Calendar | feed not accepted | Manual | deployed URL test before done | fix headers/ICS |

Critical silent gaps: none allowed. Apple Calendar subscription is manual but blocking for completion.

## Test plan

### Unit tests with Vitest

- `steam-client`:
  - accepts SteamID64
  - extracts SteamID64 from allowed profile/wishlist URLs if implemented
  - rejects vanity URL and non-Steam URL
  - builds wishlist URL exactly
  - maps timeout, 403, unexpected HTML, private/hidden wishlist, empty wishlist
  - respects item cap and concurrency limit

- `event-mapper`:
  - exact release date becomes release event
  - TBD / Coming Soon / year-only / month-only are excluded from feed
  - fixed Steam major event becomes all-day range
  - empty releases still allow major events

- `ics-generator`:
  - golden output includes VCALENDAR and VEVENT
  - stable UID does not derive from title
  - release event uses `DTSTART;VALUE=DATE`
  - range event uses exclusive `DTEND;VALUE=DATE`
  - description/title escaping works for comma, semicolon, backslash, newline

### E2E tests with Playwright

- Landing page renders hero copy and SteamID64 input.
- Valid mocked SteamID64 shows preview with release event and major event.
- Invalid input shows clear error and does not fetch arbitrary URL.
- Private/hidden wishlist shows fallback copy.
- Preview exposes feed URL.
- Feed URL returns `text/calendar` and contains expected events.

- Deploy to Vercel.

- Subscribe in Apple Calendar using deployed HTTPS/webcal URL.

## Performance plan

- Add 10s external fetch timeout.
- Add short cache for wishlist/app metadata fetches. Prototype cache can be in-process or Next/Vercel fetch cache, documented as best effort.
- Add item cap: first 100 wishlist apps in prototype.
- Add metadata concurrency limit: 5.
- Avoid fetching metadata when wishlist response already includes exact release information.
- Do not promise instant updates. Calendar client refresh cadence controls timing.

## Security and abuse plan

- Never fetch arbitrary user-provided URLs.
- Only parse SteamID64 and known Steam host URL shapes.
- Reject vanity URL for prototype with clear copy.
- Enforce input length limits.
- Enforce item cap.
- Avoid logging full wishlist contents in production logs.
- Feed URL exposes SteamID64 by design in prototype; document this as a prototype limitation.

## Worktree parallelization strategy

Sequential implementation, limited parallelization opportunity for the first prototype because the ingestion spike determines the shape of UI and feed routes.

After ingestion succeeds, two lanes can run in parallel:

| Step | Modules touched | Depends on |
|------|-----------------|------------|
| Ingestion spike | steam-client | — |
| ICS generator | ics-generator, tests | — |
| Preview UI/routes | app routes/components | Ingestion spike, event-mapper shape |
| Feed route | app routes, ics-generator, event-mapper | Ingestion spike, ICS generator |
| E2E tests | e2e/tests | Preview UI/routes, feed route |

Parallel lanes:

- Lane A: Ingestion spike → event mapper → preview route.
- Lane B: ICS generator + golden tests.
- Lane C: UI + E2E after A and B produce stable interfaces.

Execution order:

1. Run Lane A and Lane B in parallel if using separate agents.
2. Merge interfaces.
3. Build feed route and UI.
4. Run E2E and manual Apple Calendar validation.

Conflict flags:

- Lane A and feed route both touch event data shape; define the internal `CalendarEvent` type before parallel work.
